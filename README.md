## What's inside

**`MaBoSSProcess`** (`viva_maboss.processes`) drives the real MaBoSS engine through
[`cmaboss`](https://pypi.org/project/cmaboss/) (BSD-3-Clause, built and published by maboss-bkmc/MaBoSS). Each
interval it writes the network (`.bnd`) and an interval configuration (`.cfg`), runs `sample_count` stochastic
trajectories, and reports:

- `node_probabilities`: the ensemble probability that each node is on, averaged over the interval's last time window
  (MaBoSS reports window averages, not instants; there are `windows_per_interval` windows, 100 by default);
- `node_state`: one joint state sampled from the ensemble's joint-state distribution over that window;
- `steps`: one per interval, the index that seeds the next interval.

Outputs are deltas against the values the input stores hold, so `map[float]` stores end at the new values whatever
they held before, including a sibling's write or a restart from a saved state.

**Coupling.** MaBoSS starts a run from per-node initial distributions only, so the Process carries one sampled joint
state and starts the next interval from exactly that state. Because the sample comes from the last window, the carried
state lags the interval's end by about half a window, `interval / (2 * windows_per_interval)`. That is an approximation,
0.5% of the interval by default; raise `windows_per_interval` to tighten it. Measured on an absorbing switch (k = 0.3,
three intervals of 1.0, 2000 single-trajectory replicates): 0.580 at 100 windows against the exact 0.593; 0.360 at
one window per interval.

**Inputs.** `node_state` is where the next interval starts; a sibling process may write it. `parameters` overrides the
network's `$name` rates, so a kinetic layer can drive the Boolean layer. Parameters are written into each interval's
`.cfg`, and every `$name` needs a default in `config['parameters']`. Rates must be finite and non-negative: a negative
rate kills the MaBoSS process (SIGBUS), so it is refused first. `cmaboss`'s `update_parameters` is not used, because on
1.0.0b34 it accepted a change and the result did not change.

**Reproducibility.** Each interval's MaBoSS seed and sampler come from `numpy.random.SeedSequence([seed, steps])`.
Distinct seeds never share streams, and a run resumed from a saved state continues the same streams. The MaBoSS seed is
kept below 2^31, because MaBoSS mishandles larger `seed_pseudorandom` values (measured: single trajectories switched on
0.64 of the time where the exact value is 0.26).

**Network size.** cmaboss ships builds for up to 64, 128, 256, 512 and 1024 nodes; the smallest that fits is used.

**Validation.** The tests run the real engine against an analytic oracle. A node that switches on at rate k and never
switches off has an on-probability whose average over [a, b] is 1 - (e^-ka - e^-kb) / (k(b - a)). A test with wide windows
separates the window average from the instant (0.62277 against 0.63212).

**Installing.** Runtime dependencies are process-bigraph, bigraph-schema, cmaboss and numpy. The dashboard is the
`dashboard` extra; `dev` includes it. The composite generator is `maboss_toggle_switch`.

## Why MaBoSS, not BoolNet

[BoolNet](https://cran.r-project.org/package=BoolNet) was the first Boolean simulator proposed for this layer. MaBoSS
was chosen instead because it fits how this ecosystem builds and runs composites. The choice can be revisited.

- **It runs where the composites run.** compose-api builds each environment from Python packages with a pixi lock.
  MaBoSS ships Python wheels on PyPI ([`cmaboss`](https://pypi.org/project/cmaboss/), manylinux x86-64 and aarch64).
  BoolNet is an R package with no Python port on PyPI, so it would need an R runtime in every environment, reached from
  Python through a subprocess or rpy2.
- **Rates, not only update rules.** MaBoSS simulates Boolean networks in continuous time, with transition rates that
  can be parameters. A kinetic layer can therefore drive the Boolean layer by setting those rates through this
  Process's `parameters` input. BoolNet updates in discrete steps (synchronous, asynchronous or probabilistic).
- **Reproducible.** Runs are seeded (`seed_pseudorandom`); the same seed gives the same result (checked).
- **Maintained, permissively licensed.** maboss-bkmc/MaBoSS is BSD-3-Clause, actively developed, and builds and tests
  `cmaboss` on Linux, macOS and Windows in its own CI.

**The cost of the choice.** BoolNet's discrete steps would make carrying the exact state from one coupling interval to
the next trivial. MaBoSS reports an ensemble's distribution, so this Process samples one joint state per interval (see
Coupling above).

**Other options looked at.** mpbn (most-permissive Boolean networks; trajectory sampling and attractor propensities)
is the closest alternative. AEON.py and PyBoolNet focus on attractors and state graphs rather than time-course
simulation. BooleanNet's own README describes it as better suited to learning. CANA and bonesis analyse or synthesise
networks rather than simulate them.

## Layout

Project code lives at the repo root; research state is grouped under `workspace/`
(the `.pbg/` machine state stays at the root like `.git/`). Directory locations come
from the `layout:` map in `workspace.yaml` — edit it to move things.

- `workspace.yaml` — canonical state (validated against `.pbg/schemas/workspace.schema.json`).
- `viva_maboss/` — your Python package (`core.py` exposes `build_core()`).
- `scripts/` — `lint-workspace.py`, `serve.sh`, helpers.
- `workspace/studies/`, `workspace/composites/`, `workspace/references/`, `workspace/datasets/` — research artifacts.
- `workspace/notes/` — friction logs, walkthroughs, agent transcripts, ADRs. See `workspace/notes/README.md` for the
  cleanup rule: **files under `notes/` survive cleanup sweeps by default**, because they're the
  input to the next round of infrastructure improvements.
- `.pbg/schemas/` — JSON schemas the lint + dashboard validate against.

## Cleanup conventions

Cleanup PRs (`chore(cleanup): …`, `chore(repo): trim …`) routinely remove generated files,
one-shot scripts, and stale planning docs. Two locations are off-limits to bulk cleanup:

- `workspace/notes/**` — see the rule in `workspace/notes/README.md`.
- `workspace/references/notes/**` — per-paper literature notes, used by the findings protocol.

If a specific file in either location is genuinely obsolete, delete it in its own commit
with a one-line justification per file. Don't bundle with unrelated cleanup.
